# ТЗ для Kimi: Система централизованного управления Suricata IDS/IPS (Go, 1000–10000 агентов)

## 1. Роль и задача

Ты — Kimi, выступаешь как ведущий Go-разработчик и архитектор. Спроектируй и реализуй
веб-платформу централизованного управления флотом Suricata IDS/IPS (https://suricata.io/).
Функциональный минимум — уровень IDSTower (https://idstower.com/), с двумя областями,
где нужно быть строго лучше:
(А) точный ответ в реальном времени: какие правила реально загружены и работают
на каждой машине прямо сейчас;
(Б) полная диагностика проблем с агентами на сенсорах.

Жёсткие рамки:
- Весь backend и агент — **Go** (1.22+).
- Флот: **от 1000 до 10000 агентов** одновременно на один серверный контур.
- Веб-интерфейс с **RBAC**: роли Администратор, Аналитик, Оператор, Наблюдатель +
  кастомные роли.
- **SSO**: подключение к корпоративным провайдерам идентичности (OIDC/SAML/LDAP).

Работай итеративно: сначала архитектура и модель данных, затем MVP, затем остальной
функционал. После каждого этапа показывай, что сделано и что дальше.

## 2. Технологический стек

- **Backend**: Go. HTTP API — chi или gin; протокол агент↔сервер — **gRPC с
  двунаправленным стримингом** поверх mTLS. Миграции — golang-migrate. Доступ к БД —
  sqlc или pgx (без тяжёлого ORM).
- **PostgreSQL** — основная БД (состояние, правила, конфигурации, RBAC, аудит).
- **Redis** — горячее состояние: presence агентов (online/offline, last seen),
  кэш actual state, распределённые блокировки, rate limiting.
- **NATS JetStream** (или Kafka) — шина задач деплоя и событий; гарантии доставки,
  ретраи, fan-out на тысячи агентов.
- **ClickHouse или VictoriaMetrics** — метрики флота (kernel drops, throughput и т.д.)
  и телеметрия; PostgreSQL для этого не использовать.
- **S3-совместимое хранилище** (MinIO) — блобы ruleset'ов, content-addressed (по хэшу);
  агенты скачивают правила по подписанным URL, а не через основной API.
- **Агент**: Go, единый статический бинарь без зависимостей, systemd-юнит, пакеты
  deb/rpm. Ресурсный бюджет агента: < 50 МБ RAM, < 1% CPU в простое.
- **Frontend**: React + TypeScript + Tailwind + shadcn/ui, локализация ru/en.
- **Аутентификация**: сессии/OIDC — на базе проверенных библиотек (coreos/go-oidc,
  crewjam/saml), без самодельной криптографии.

## 3. Архитектура под 1000–10000 агентов

Это ключевое архитектурное требование, заложи его в каждое решение:

- **Протокол**: агент сам устанавливает исходящее gRPC-соединение (bidirectional stream)
  к серверу — работает за NAT без входящих портов. Heartbeat — лёгкие сообщения внутри
  стрима каждые 30 с (не отдельные HTTP-запросы). 10k одновременных стримов — штатный
  режим для Go; заложи graceful handling reconnect-штормов (jitter при переподключении,
  exponential backoff на агенте).
- **Горизонтальное масштабирование сервера**: stateless API-узлы за балансировщиком;
  узлы-«концентраторы» агентских стримов с консистентной маршрутизацией агент→узел
  (через Redis-реестр); задачи агентам маршрутизируются через NATS на нужный узел.
- **Деплой на тысячи хостов**: рассылка волнами (batch size, concurrency limit,
  pause/resume, canary-группа первой); правила раздаются как content-addressed блобы
  из S3 по хэшу — один ruleset скачивается один раз на хост, дедупликация по хэшу
  между кластерами.
- **Телеметрия**: агенты шлют метрики батчами (раз в 60 с), сервер пишет в
  ClickHouse/VictoriaMetrics; в PostgreSQL — только агрегированное текущее состояние.
- **БД**: партиционирование таблиц событий/аудита по времени; индексы под запросы
  матрицы «правила × хосты»; пагинация keyset-based везде в API.
- **Деградация**: при недоступности Redis/NATS/S3 сервер и агенты деградируют
  предсказуемо (агент продолжает работать на последней конфигурации и буферизует
  телеметрию на диск с ротацией).

## 4. Модель флота

Организация → Кластеры → Хосты → Инстансы Suricata (несколько инстансов на хосте —
учитывать везде: в деплое, метриках, UI).

Онбординг без переустановки: агент обнаруживает существующий сервис Suricata, бинарь
(включая сборку из исходников), suricata.yaml, каталоги правил и логов, интерфейсы
захвата, версию и флаги сборки — и показывает пользователю для подтверждения.
Поэтапная передача контроля: 6 независимых capability на кластер/хост (мониторинг,
правила, ротация логов, управление сервисом, пакеты, конфигурация); дефолт
консервативный. Бэкап перед любым изменением.

## 5. Базовый функционал (уровень IDSTower)

1. **Правила**: мастер-репозиторий; импорт файлами и из фидов (ET Open/Pro и др.);
   парсинг/валидация при импорте; жизненный цикл (enabled/disabled/expired/under
   review/deleted); категории и теги; массовые операции; сохранение тюнинга аналитика
   (priority, threshold, отключение) между ревизиями фида; гранулярный таргетинг
   (все кластеры / выбранные / все кроме выбранных / шаблоны деплоя на кластеры,
   хосты, инстансы); история изменений; экспорт (text, STIX 2.1, Suricata Dataset).
2. **IOC/TI**: жизненный цикл IOC (фиды → парсинг → скоринг → автодеплой →
   автоистечение); коннекторы TAXII/STIX 2.0/2.1, MISP, generic (text/CSV/JSON);
   автогенерация правил по IOC; ссылки на VirusTotal/ipinfo.
3. **Конфигурации**: централизованный редактор suricata.yaml (структурный + raw),
   валидация `suricata -T` на агенте до применения, профили с наследованием
   кластер→хост→инстанс, история с diff и откатом.
4. **Мониторинг**: метрики Suricata (kernel drops, flow, detect), статус сервиса,
   CPU/RAM/диск хоста; пересылка EVE-алертов через Filebeat/Vector в SIEM;
   дашборды флот/кластер/хост.
5. **Платформа**: полный REST API (OpenAPI), API-токены, аудит-лог, уведомления
   (email/webhook/Telegram).

## 6. КЛЮЧЕВОЕ ТРЕБОВАНИЕ А: «Какие правила на какой машине работают прямо сейчас»

Система обязана в любой момент отвечать: какой набор правил РЕАЛЬНО загружен движком
Suricata на конкретном инстансе.

- **Desired state**: версионируемый набор (sid + ревизия + статус), рассчитанный
  сервером для каждого инстанса из шаблонов деплоя и таргетинга. Идентификатор —
  версия + хэш ruleset.
- **Actual state**: агент после каждого деплоя и периодически (раз в 5 мин) отчитывается:
  список загруженных движком правил; список failed rules с текстом ошибки парсера;
  хэш ruleset-файла на диске; время и результат последнего reload/restart.
  Кэш actual state — в Redis, персистентная история — в PostgreSQL, с таймстемпом
  «данные актуальны на …».
- **Статусы соответствия (drift detection)** на каждый инстанс:
  In sync / Pending deployment / Partial (часть правил не загрузилась — какие и
  почему) / Drift (факт ≠ desired, показать diff) / Stale (агент молчит дольше порога —
  данным нельзя доверять).
- **Деплой считается успешным только по подтверждению агента о фактической загрузке
  правил движком**, а не по коду возврата команды доставки файла.
- **UI**: матрица «правила × хосты/инстансы» (виртуализация под 10k хостов и 50k+
  правил); страница инстанса (версия ruleset, активные/failed правила, история
  деплоев: версия, время, инициатор, результат); глобальная сводка флота по статусам
  соответствия с drill-down.
- Производительность: расчёт статусов соответствия — инкрементальный, по событиям,
  а не полным пересчётом; сводка флота из 10k инстансов открывается < 2 с.

## 7. КЛЮЧЕВОЕ ТРЕБОВАНИЕ Б: Проблемы с агентами

- **Мониторинг**: heartbeat в gRPC-стриме (версия агента и Suricata, uptime, last seen,
  латентность); статусы Online / Degraded / Offline / Updating / Error; флот-вид
  версий агентов, массовое обновление агентов волнами, матрица совместимости
  агент↔сервер.
- **Автодетект инцидентов** (каждый — объект с severity, контекстом, рекомендацией):
  агент offline или flapping; сервис Suricata упал после деплоя → **автоматический
  откат** на предыдущую рабочую версию правил/конфига; failed rules; конфигурация не
  прошла `suricata -T`; высокий % kernel drops; диск заполнен / логи не ротируются;
  рассинхронизация часов агент↔сервер; устаревший/несовместимый агент; сбой
  автообновления; drift дольше порога.
- **Реагирование**: уведомления с дедупликацией и эскалацией; действия из UI —
  перезапуск агента/сервиса, повторный деплой, откат, сбор диагностического бандла
  одной кнопкой; ретраи с backoff; деплой на проблемный хост блокируется с понятным
  сообщением.
- При 10k агентов: детекторы инцидентов — потоковые (по событиям heartbeat/отчётов),
  не периодическим полным обходом флота.
- **Передача состояния и логов агента в систему**: агент регулярно и по событиям
  передаёт на сервер полное состояние (версии, статус сервиса Suricata, версия
  применённого ruleset/конфига, результат последних операций, ресурсы) И свои
  операционные логи: каждое действие агента (получение задачи, скачивание ruleset,
  применение, reload/restart, откат, ошибки) логируется локально и батчами
  отправляется на сервер по gRPC-стриму. Уровень детализации логов (debug/info/
  warn/error) настраивается с сервера централизованно — на кластер, хост или
  отдельный агент, без рестарта. На сервере логи агентов доступны в UI с поиском
  и фильтрами (по хосту, уровню, периоду, операции); error-записи автоматически
  поднимают/обогащают инциденты.
- **Локальное логирование агента в файл на хосте с ротацией**: агент пишет
  структурные JSON-логи (slog) в локальный файл (по умолчанию
  /var/log/<имя-агента>/agent.log) с ротацией по размеру и количеству файлов
  (lumberjack или собственная ротация; параметры — max size, max backups, max age —
  настраиваются с сервера). Локальный файл — источник истины при потере связи:
  агент буферизует записи и досылает их на сервер после восстановления канала
  (at-least-once, с дедупликацией по sequence number). Ротация не должна терять
  недоставленные на сервер записи.

## 8. RBAC в веб-интерфейсе и API

- Встроенные роли:
  - **Администратор** — полный доступ: пользователи, роли, SSO, хосты, агенты,
    все операции.
  - **Оператор развёртывания** — деплой правил/конфигураций, управление сервисами
    и агентами, откаты; без управления пользователями и политиками доступа.
  - **Аналитик** — управление правилами, IOC, фидами, тюнинг, просмотр алертов
    и состояния; без деплоя и управления хостами (или деплой только через
    подтверждение оператором — настраивается).
  - **Наблюдатель** — read-only: дашборды, статусы, алерты, инциденты.
- **Кастомные роли**: набор гранулярных разрешений (rules.read/write/deploy,
  ioc.*, hosts.*, agents.*, config.*, users.*, incidents.*, audit.read и т.д.).
- **Scoping**: привязка роли к организации или к подмножеству кластеров
  (аналитик видит/меняет только свои кластеры).
- Единая проверка разрешений в middleware REST API и в gRPC-методах управления;
  UI скрывает недоступные действия, но вся авторизация — на backend.
- **Полный аудит-лог всех действий в веб-интерфейсе и API**: логируется КАЖДОЕ
  действие пользователя — вход/выход (включая SSO), просмотр чувствительных данных,
  создание/изменение/удаление правил, IOC, конфигураций, шаблонов, пользователей,
  ролей, SSO-провайдеров, деплои, откаты, действия над агентами и сервисами.
  Каждая запись: кто (пользователь/сессия/API-токен), откуда (IP, user-agent),
  что (тип действия, объект, параметры), когда, результат (успех/отказ + причина),
  diff «было → стало» для изменений. Хранение с партиционированием и retention-
  политикой; поиск и фильтрация в UI; экспорт; защита от подделки (append-only,
  опционально — цепочка хэшей записей). Аудит недоступен для удаления через UI/API
  никому, включая администраторов.

## 9. SSO и управление идентичностью

- **OIDC (OAuth2 Authorization Code + PKCE)** — основной протокол: Keycloak,
  Microsoft Entra ID, AD FS, Okta, Authentik и любой совместимый IdP.
- **SAML 2.0** — второй протокол для корпоративных IdP.
- **LDAP/AD** — опционально: bind-аутентификация и чтение групп.
- Несколько провайдеров одновременно, привязка провайдера к организации.
- **Маппинг групп IdP → роли системы** (таблица соответствий, приоритеты при
  нескольких группах); смена группы в IdP меняет роль при следующем логине.
- **JIT-провижининг**: пользователь создаётся при первом входе; деактивация в IdP
  блокирует доступ (проверка при refresh токена/повторном логине).
- **Break-glass**: минимум один локальный администратор вне SSO (на случай
  недоступности IdP), с отдельным аудитом его входов.
- Сессии: короткоживущий access token + refresh, отзыв сессий администратором,
  принудительный logout всех сессий пользователя.
- API-токены для автоматизации — с областями действия (scopes), сроком жизни и аудитом.

## 10. Нефункциональные требования

- Безопасность: mTLS сервер↔агент (индивидуальные сертификаты агентов, ротация),
  шифрование секретов в БД, rate limiting, защита от replay в протоколе агента.
- Надёжность: идемпотентность всех операций деплоя; офлайн-режим агента; бэкап
  перед изменениями; миграции БД только вперёд-совместимые.
- Наблюдаемость самой системы: Prometheus-метрики сервера, структурные логи (slog),
  трейсинг (OpenTelemetry).
- Установка: docker-compose для оценки; Helm-чарт или systemd-пакеты для продакшена.
- Тесты: unit + интеграционные, включая симулятор флота (Go-утилита, поднимающая
  N виртуальных агентов для нагрузочного теста на 1000–10000 соединений).

## 11. Порядок работы (что выдать и в какой последовательности)

1. Архитектура: диаграмма компонентов, схема протокола агент↔сервер (gRPC,
   сообщения heartbeat/отчёт/задача/ack), схема масштабирования на 10k агентов.
2. Модель данных (ER + миграции): организации, кластеры, хосты, инстансы, правила,
   ревизии, фиды, IOC, шаблоны деплоя, desired/actual state, деплои, агенты,
   инциденты, пользователи, роли, SSO-провайдеры, аудит.
3. OpenAPI-спецификация REST API + .proto контракт агента.
4. MVP: сервер (Go) + агент (Go) + UI, покрывающие: онбординг хоста, импорт правил,
   таргетинг, волновой деплой с подтверждением по факту, витрину desired vs actual
   (п. 6), мониторинг агентов и инциденты (п. 7), логин через OIDC + роли (п. 8–9).
5. Симулятор флота и нагрузочный тест: 1000 и 10000 агентов, метрики latency
   heartbeat, время волнового деплоя, нагрузка на БД.
6. Далее итерациями: IOC/TI, конфигурации, SAML/LDAP, дашборды, экспорт.

Критерии приёмки MVP: деплой ruleset на 1000 агентов < 5 минут; статус соответствия
по любому инстансу актуален не старше 5 минут; при отключении 10% агентов инциденты
создаются < 60 с; вход через OIDC с маппингом групп в роли работает end-to-end.

## 12. Организация работы: чанки, чекпоинты, защита от потери прогресса

Контекст диалога (токены) — расходуемый ресурс. Работай так, чтобы прерывание
сессии в любой момент НЕ приводило к потере результата:

- **Мелкие чанки**: каждая единица работы — законченный, проверяемый кусок
  (одна миграция, один proto-контракт, один gRPC-метод + тест, один UI-экран).
  Не делай гигантских неделимых этапов.
- **Коммит после каждого чанка**: git-репозиторий с первого шага; коммит сразу
  после того, как чанк собирается и проходит тесты. Рабочее дерево всегда должно
  собираться — никаких «накоплю изменения и закоммичу потом».
- **Файл состояния PROGRESS.md в корне репозитория** — обновляй после КАЖДОГО
  чанка, до того как контекст подойдёт к концу:
  - текущая фаза и номер чанка;
  - что уже сделано (список со ссылками на коммиты/файлы);
  - что делать следующим шагом (конкретно: файл, функция, ожидаемый результат);
  - ключевые архитектурные решения и договорённости (одной строкой каждое);
  - как поднять окружение и запустить то, что есть (команды);
  - известные проблемы и отложенные задачи.
- **Правило возобновления**: в начале каждой новой сессии первым делом прочитай
  PROGRESS.md и `git log` — и продолжай с записанного следующего шага, не
  переспрашивая пользователя о том, что уже зафиксировано.
- **Немедленная запись на диск**: любой большой артефакт (спецификация, миграция,
  proto, код) сразу сохраняй в файл — не держи его только в тексте ответа.
- **Чекпоинт при нехватке контекста**: если чувствуешь, что контекст близок к
  исчерпанию — не начинай новый чанк. Доведи текущий до компилируемого состояния
  (или откати недоделанное), закоммить, обнови PROGRESS.md и явно сообщи:
  «чекпоинт сохранён, продолжай со следующего шага из PROGRESS.md».
- **Частичный результат лучше полного, но несохранённого**: лучше 3 закоммиченных
  чанка из 5, чем 5 написанных и потерянных.
- Документы этапов (архитектура, ER, OpenAPI, proto) тоже хранятся в репозитории
  в docs/ и версионируются вместе с кодом, а не только в переписке.
- **FEATURES.md — реестр реализованного функционала**: веди таблицу «пункт ТЗ →
  статус (не начато / в работе / готово / протестировано) → где реализовано
  (пакеты, файлы, endpoint'ы, экраны) → номер чанка/коммита». Обновляй при каждом
  изменении статуса. По этому файлу в любой момент должно быть видно, что система
  уже умеет, а что нет — без чтения всего кода.
- **CHANGELOG.md — журнал изменений**: после каждого чанка записывай, что
  поменялось, в формате Keep a Changelog (Added / Changed / Fixed / Removed):
  дата, версия или номер чанка, список изменений с указанием затронутых компонентов
  (server / agent / ui / db / api / proto). Записывай и ломающие изменения
  (миграции БД, изменения контрактов proto/API) с пометкой BREAKING и инструкцией
  по обновлению.
- PROGRESS.md (куда идём), FEATURES.md (что уже умеем) и CHANGELOG.md (что
  менялось) — три обязательных живых документа; их обновление — часть definition
  of done каждого чанка, а не опция.
