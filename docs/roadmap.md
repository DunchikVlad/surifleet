## Уже готово (для контекста)

- Требование А (desired/actual state, волновой деплой, матрица
  «правила × инстансы», подтверждение загрузки движком) — 🧪 живьём.
- IOC/TI целиком (5.2): жизненный цикл, 6 коннекторов фидов
  (generic/et_open/et_pro/taxii/stix/misp), cron-расписания,
  автогенерация правил, отзыв при revoke/expire.
- Auth/RBAC (8): локальные пользователи, сессии, API-токены со scopes,
  4 встроенные роли + кастомные, scoping по кластерам (CRUD флота,
  таргетинг деплоев, матрица), аудит (append-only + цепочка хэшей +
  экспорт csv/json), break-glass. SSO: OIDC ✅, SAML/LDAP — код есть,
  без живого IdP e2e.
- Мониторинг (часть 5.4): метрики host.* + suricata.* (eve stats) →
  ClickHouse, вкладка «Метрики», TTL retention 30 дней; пересылка
  EVE-алертов в SIEM (syslog UDP/TCP, CEF/JSON) — проверено живьём.
- Требование Б (частично): heartbeat/online/offline + свипер тихой
  смерти, логи агента → ClickHouse, watchdog автоотката после деплоя
  (12c-2), диагностика завершения агента (exit-лог).

## Остаток по эпикам

### Эпик «Правила» (5.1, 🚧 → ✅)

- Экспорт правил: `GET /rules/export?format=text|stix|dataset`
  (text = .rules — почти бесплатно, рендерер ruleset уже есть;
  stix — bundle из rules; dataset — Suricata Dataset-форматы).
  ~1 чанк.
- Таргетинг правил по кластерам/хостам на уровне ruleset-сборки
  (сейчас таргетинг — на уровне деплоя). ~1 чанк, уточнить по ТЗ.

### Эпик «Конфигурации» (5.3, ⬜ — самый крупный)

- Редактор suricata.yaml в UI (по хосту/инстансу), версии конфигураций.
- Валидация `suricata -T` на агенте перед применением (конвейер деплоя
  конфигов — переиспользовать волновой деплой правил: отдельный тип
  задачи `deploy_config`, бэкап, откат, верификация).
- Профили конфигураций (шаблоны с переменными по кластеру).
- Откат конфигурации (append-only история, rollback = новый деплой).
- Оценка: 3–4 чанка. Требования Б (watchdog) переиспользуются.

### Эпик «Мониторинг» (5.4, 🚧)

- SIEM-конфиг с сервера: siem_addr/protocol/format сейчас в agent.yaml —
  перенести в ConfigPush (кластер/хост/агент), proto-поля + агент.
  ~1 чанк.
- Дашборды флот/кластер/хост: агрегаты по метрикам (выборки по
  cluster/host), страница с картой флота. ~1–2 чанка.
- Метрики Suricata глубже: per-thread, eve.json drop rate в %,
  алерты/сек. ~1 чанк.

### Эпик «Проблемы с агентами» (требование Б, 🚧/⬜)

- Автодетект инцидентов (ТЗ: ~10 типов — мёртвый агент, failed reload,
  drift > порога, рассинхронизация часов, устаревший агент, сбой
  автообновления и т.д.): таблица incidents уже в схеме (000001),
  детекторы по событиям heartbeat/отчётов, дедуп по fingerprint
  (частичный UNIQUE уже есть). ~2 чанка.
- Статусы агента Degraded/Error (сейчас online/offline): вывод из
  метрик/инцидентов. ~1 чанк.
- Реагирование: действия из UI (перезапуск сервиса/агента — proto уже
  имеет типы задач?), повторный деплой одной кнопкой, диагностический
  бандл (агент собирает логи/конфиги/статусы → на сервер). ~2 чанка.
- Уведомления (email/webhook/Telegram) с дедупликацией и эскалацией.
  ~1–2 чанка. MVP-формат: webhook + Telegram-бот.

### Эпик «SSO доводка» (8–9, 🚧)

- E2E с mock-IdP (OIDC) и mock-LDAP на стенде; SAML — хотя бы
  валидация SP/IdP метаданных на mock. ~1 чанк.
- Приоритеты при маппинге нескольких групп (сейчас объединение).
  Мелочь.
- Деактивация пользователя в IdP → блокировка при refresh (частично
  есть; проверить).

### Эпик «Модель флота» (4)

- 6 capability поэтапной передачи контроля (таблица capabilities есть,
  реализована только `rules`): monitoring, config, service, files,
  network (по ТЗ п. 4). ~1–2 чанка после эпика «Конфигурации».

### Нефункциональные (10)

- Авторотация сертификатов агентов (за 30 дней до истечения;
  сейчас — перевыпуск через Enroll). ~1 чанк.
- Симулятор флота cmd/fleetsim (каталог есть — проверить состояние):
  1k/10k виртуальных агентов для нагрузочного. ~1–2 чанка.
- docker-compose полного продукта (сервер+UI, не только инфра) для
  оценки. ~1 чанк.
- Helm-чарт / systemd-пакеты для продакшена. ~1–2 чанка.
- Rate limiting API (п. 10). ~0.5 чанка.

### Техдолг и гигиена

- Тест samlauth TestKeyPairPersistedAcrossRestarts падает на Windows
  (NTFS-права 0600) — пометить t.Skip на windows или chmod через ACL.
- CRLF при checkout на Windows: `gofmt -l` флагает подтянутые файлы;
  добавить .gitattributes (* text=auto eol=lf) и нормализовать.
- Браузерная проверка UI (все проверки до сих пор — HTTP; форму входа
  и новые вкладки стоит открыть глазами).
- `npm audit`/обновление зависимостей web/ перед релизом.
- Vanilla-артефакты: ссылки на старый UI вычищены; проверить, что
  в README нет устаревших инструкций.

## Предлагаемый порядок (волны)

**Волна 1 — добивка эксплуатируемого MVP** (мелкие, быстрые, закрывают
«боль оператора»):
1. Экспорт правил (5.1) — 1 чанк.
2. SIEM-конфиг через ConfigPush (5.4) — 1 чанк.
3. Авторотация сертификатов агентов — 1 чанк.
4. Гигиена: .gitattributes + samlauth-тест skip + фикс FEATURES
   (watchdog 12c-2 не отражён в строке «Автооткат»).

**Волна 2 — конфигурации (5.3)** — самый большой кусок MVP:
редактор → версии → деплой-конвейер конфигов → профили → откат.
3–4 чанка.

**Волна 3 — требование Б целиком**: инциденты (детекторы) → статусы
Degraded/Error → действия из UI + диагностический бандл → уведомления.
4–5 чанков.

**Волна 4 — SSO доводка + scale**: mock-IdP e2e, приоритеты групп;
fleetsim 1k → 10k, нагрузочное; docker-compose оценки, Helm.
3–4 чанка.

**Волна 5 — capability-модель (6 ступеней передачи контроля)** — после
волны 2 (зависит от деплоя конфигов).
