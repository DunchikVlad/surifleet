### KI-2. Telegram: нет уведомления «агент снова онлайн»

- **Статус**: открыто (доработка)
- **Добавлено**: 2026-10-10 (по замечанию с живого стенда)
- **Симптом**: при переходе агента в offline уведомление приходит, а при
  возвращении агента в online — нет. Дежурный не понимает, восстановился
  ли сенсор, не заглядывая в UI.
- **Что сделать**: в переходе статуса агента offline → online (там же,
  где шлётся offline-уведомление — обработчик heartbeat/presence)
  отправлять уведомление «агент снова онлайн» (recovery). Учесть
  дедупликацию/флапы: не спамить при частых переподключениях
  (например, recovery только если offline длился дольше N минут или
  уже ушло offline-уведомление).
- **Проверка**: остановить агента на .67 → дождаться offline-уведомления →
  запустить → получить «агент онлайн» с теми же атрибутами.

- **Статус**: открыто (доработка)

- **Симптом**: уведомления об агенте не содержат IP-адрес и hostname —

- **Проверка**: любое агент-событие → в Telegram видны hostname и IP.

- **Проверка**: задеплоить заведомо битый ruleset (ошибка парсера) →
  задача failed → в Telegram пришло уведомление с причиной.

### KI-1. Цепочка хэшей аудита: запись не проходит пересчёт hash

- **Статус**: открыто
- **Найдено**: 2026-10-10, smoke-прогон после переката (коммит `728e8fd`)
- **Симптом**: `GET /api/v1/audit_log/verify?limit=200` → `ok:false`,
  `broken_at: 4e34bdef-c94c-4fe3-8e90-137b4b8e0a96`,
  причина «hash записи не совпадает с содержимым (подделка полей?)».
  Проверка останавливается на первой битой записи — записи старше не
  проверяются, после фикса нужен повторный прогон с limit по всей таблице.
- **Запись**: `rules.update` от 2026-10-07T20:00:33Z, actor admin,
  diff содержит только `updated_at` (before/after):
  `{"after":{"updated_at":"...33.279505Z"},"before":{"updated_at":"...25.62078Z"}}`.
- **Воспроизведение**: `curl -H "Authorization: Bearer $TOKEN"
  http://192.168.31.28:8080/api/v1/audit_log/verify?limit=200`.
- **Гипотеза**: рассинхрон канонизации поля `diff` между записью и
  верификацией. При записи хэш считается от `string(e.Diff)` — исходной
  сериализации (`internal/auditdiff/auditdiff.go:57`, `json.Marshal` мапы);
  в БД колонка `jsonb`, который нормализует документ (порядок ключей,
  числа, пробелы); при verify (`internal/store/audit_chain.go`,
  `VerifyChain`) в хэш идёт уже jsonb-нормализованный текст. Для записей
  без diff (или с diff, чья сериализация совпала с jsonb-формой)
  расхождения нет — поэтому ломается не каждая запись. Дополнительный
  подозреваемый: HTML-эскейпинг `json.Marshal` (`<`, `>`, `&`) — jsonb
  его не воспроизводит.
- **Что сделать**: канонизировать diff одинаково на обеих сторонах —
  например, при записи прогонять diff через round-trip
  `SELECT $1::jsonb::text` (или собственная канонизация JSON: сортировка
  ключей, компактная форма, без HTML-эскейпа — `json.Encoder` с
  `SetEscapeHTML(false)`) и хэшировать именно эту форму. Регрессионный
  тест: запись аудита с diff (PATCH правила) → `VerifyChain` ok.
  Историческую битую запись либо пометить известным исключением, либо
  пересчитать (с записью об этом в аудит).
